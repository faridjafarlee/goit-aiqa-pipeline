# Правила побудови чекліста (reference)

Джерела: ISTQB CTFL v4.0, ISTQB CTAL-TA v4.0,
загальноприйняті практики requirements-based testing.

## Що таке пункт чекліста

За ISTQB, test condition є аспектом або подією компонента
чи системи, який можна перевірити одним або кількома
тест-кейсами. Пункт чекліста є атомарною test condition
з однозначним очікуваним результатом.

Пункт чекліста відповідає на питання «що перевірити
і який результат очікується». Тест-кейс (наступний скіл)
відповідає на питання «як перевірити».

## Якісні атрибути пункту

### Атомарність

Один пункт = одна перевірка з одним pass/fail.
«Кнопка видима і клікабельна» дає два пункти.
Якщо пункт може бути «частково pass», розбий його далі.

### Трасованість

Кожен пункт має REQ-ID. Кожна вимога має хоча б один
пункт. Немає пунктів без джерела і немає вимог
без жодної перевірки.

### Однозначність

Одна інтерпретація. Будь-які дві людини, прочитавши пункт,
мають зробити однаковий висновок pass/fail.

### Самодостатність

Пункт зрозумілий без відкриття requirements-файлу
і без контексту інших пунктів.

### Незалежність

Пункт можна перевірити окремо. Замість «після виконання
REQ-1.2 результати оновлюються» пиши «при виборі категорії
результати оновлюються».

### Відсутність дублювання

Одна перевірка не повторюється в різних пунктах,
навіть під різними REQ-ID.

### Консистентність

Однотипні елементи отримують ідентичний базовий набір
перевірок. Різниця тільки в специфічних перевірках
поверх базового набору.

## Правила формулювання

Пункт складається з двох частин:

- Що перевіряється (елемент, стан, поведінка)
- Який очікуваний результат (значення, стан, текст)

Обидві частини обов'язкові. Пункт без очікуваного
результату не є перевіркою.

### Заборонені слова

Ці слова роблять перевірку неоднозначною, не використовуй їх:

- «коректно», «правильно», «належним чином»
- «відповідний», «адекватний», «прийнятний»
- «за потреби», «за необхідності»
- «кілька», «деякі», «достатньо»
- «швидко», «плавно», «зручно»
- «добре виглядає», «нормально працює»

Замість них пиши конкретне значення, стан, текст, число.

## Декомпозиція вимоги на пункти

### Процес по ISTQB

Test Analysis: вимога → test conditions (аспекти,
які потрібно перевірити). Кожна test condition стає
пунктом чекліста.

Для кожної вимоги послідовно визнач:

1. Які елементи або стани описує вимога
2. Які дії або поведінки описує вимога
3. Які умови або обмеження описує вимога
4. Чи є залежності від інших вимог

Кожен пункт з кроків 1-4, який має однозначний pass/fail,
стає пунктом чекліста.

### Типи перевірок

Не кожен тип застосовний до кожної вимоги.
Генеруй тільки ті, що випливають з конкретної вимоги.

Позитивний сценарій: основна поведінка працює
як описано (happy path). Застосовний завжди.

Негативний сценарій: поведінка при невалідних діях
або даних. Тільки коли вимога описує інтерактивність.

Граничні значення: поведінка на межах. Тільки коли
вимога описує числові або текстові обмеження.

Стан за замовчуванням: початковий стан до дій
користувача. Тільки коли вимога описує елемент
з початковим станом.

Стани елементів: видимість, активність залежно
від умов. Тільки коли вимога описує умовну поведінку.

Переходи між станами: зміна стану при дії.
Тільки коли вимога описує зміну стану.

Скидання: повернення до початкового стану.
Тільки коли вимога описує скидання або очищення.

Валідація: правила і повідомлення. Тільки коли
вимога описує валідацію.

Дані: поля, формати, маппінги. Тільки коли
вимога описує конкретні поля або формати даних.

Комбінації умов: поведінка при різних комбінаціях.
Тільки коли вимога містить кілька незалежних умов.

Відповідність UI: лейбли, тексти, розташування.
Тільки коли вимога описує конкретний текст або позицію.

### Перевірки на стиках вимог

Після декомпозиції кожної вимоги окремо перевір
групи повʼязаних вимог. На стиках між вимогами
бувають перевірки, які не видно при декомпозиції
окремої вимоги: залежності, конфлікти, спільні стани.

## Критерій достатності

### Достатньо коли

- Кожна вимога має хоча б одну перевірку
- Кожен пункт має рівно один pass/fail
- Кожен пункт зрозумілий без контексту інших пунктів
- Однотипні елементи мають однаковий базовий набір

### Надмірно коли

- Пункти дублюють один одного іншими словами
- 10+ пунктів на просту вимогу з одним елементом
і однією поведінкою
- Пункт перевіряє деталь, якої немає у вимозі

## Базовий набір для типових елементів

Мінімальний scope для типових UI-елементів.
Використовуй його як відправну точку і генеруй
тільки ті пункти, які випливають з конкретної вимоги.

Селект: присутність, тип елементу, опції,
дефолтний стан, основна дія, скидання.

Поле вводу: присутність, тип поля, лейбл,
placeholder (якщо є), дефолтне значення (якщо є),
валідація (якщо описана), обмеження (якщо описані).

Кнопка: присутність, текст, дія при кліку,
стани і умови переходу.

Таблиця / список: присутність, колонки/поля,
дані відображаються, сортування (якщо є),
пагінація (якщо є), порожній стан.

## Фільтрація зайвих перевірок

Не генеруй перевірки на:

- стандартну поведінку браузера або платформи
- деталі реалізації (архітектура, кеш, бібліотеки)
- загальну інфраструктуру (серверні помилки, таймаути)
- граничні значення, де вимога не описує обмежень
- негативні сценарії для вимог без інтерактивності
- UX-деталі (анімації, таймінги, hover), не описані у вимозі
- поведінку, якої немає у вимогах

## Антипатерни

Дублювання через перефразування.
«Кнопка Save присутня» і «Кнопка Save відображається»
описують один пункт двічі. Видали дублікат.

Реалізація замість поведінки.
«API повертає 200» (заради самого коду 200) чи «Компонент
використовує useEffect» описують деталі реалізації, чекліст їх
не перевіряє.

Виняток: якщо сама вимога прямо описує результат на рівні
даних чи API (напр. «створюється запис зі статусом X»,
«ендпоінт повертає таке-то тіло»), це вже перевірка поведінки,
і такий пункт допустимий. Формулюй його як цю поведінку,
а не як факт виклику коду.

Неатомарний пункт.
«Фільтр присутній і при виборі фільтрує результати»
містить два пункти: присутність і фільтрацію. Розбий його.

Залежний пункт.
«Після виконання REQ-1.2 результати оновлюються».
Пункт має бути самодостатнім.

Вигадана перевірка.
«Список завантажується за 2 секунди». Якщо вимога
не описує перформанс, такого пункту не має бути.

Неоднозначне формулювання.
«Фільтрація працює коректно» не пояснює, що означає "коректно".
Краще так: «Вибір категорії Electronics відображає
тільки товари категорії Electronics».

## Доповнення (урок 4)

### Поверхня перевірки: не лише UI
Очікуваний результат може спостерігатися в UI, даних (БД), API або платіжній системі.
Якщо результат видно на кількох поверхнях, на кожну потрібен окремий атомарний пункт («зберігається і відображається» дає два пункти).
Пункт на API/БД додавай лише тоді, коли результат визначено у вимозі. Інакше це деталь реалізації.
Хто виконує перевірку (backend чи web), вирішують наступні етапи через surface-теги.

### Оракул вимоги чи деталь реалізації
Два питання: чи випливає результат із вимоги? чи можна його спостерігати й однозначно оцінити?
«API повертає 200» (код не визначено) прибери. «Сира відповідь 403 не показується користувачу» (є у вимозі) залиш.

### Перевірки на стиках вимог
Пункт на стику отримує ID тієї вимоги, яка містить очікуваний результат. Повʼязану вимогу вкажи в тексті
(напр. «…помилка "X" (активний стан кнопки: REQ-2)»), щоб coverage-critic відновив звʼязок.
Якщо реакцію на комбінацію умов не визначено, це прогалина для грумінгу. «Логічний» результат не вигадуй.

### Прибрати / переписати / залишити
| Рішення | Коли |
|---|---|
| Прибрати | Вигадана поведінка, дубль, немає підстави у вимогах |
| Переписати / розділити | Є підстава, але пункт неатомарний, залежний або неоднозначний |
| Залишити | Спостережуваний результат із вимоги, відповідає 7 атрибутам |

Після видалення: чи не лишилась вимога без пунктів? чи не зник застосовний тип перевірки?

### Вимога без власних пунктів
Допустимо лише тоді, коли вимога не має окремого спостережуваного результату і її зміст повністю
перевіряють інші пункти. У такому разі під заголовком дай пояснення з їхніми ID. Окремий спостережуваний
результат, який неможливо перевірити доступними поверхнями, записуй в обмеження покриття, а не як побічне посилання.

### Прийоми самоперевірки
- «Розділіть навпіл»: якщо дві частини мають окремі очікувані результати, це два пункти.
- Ctrl+F кожного числа/тексту в requirements-файлі; «Звідки я це знаю?» (якщо відповідь «логічно», прибери пункт).
- Читай чекліст знизу вгору; рахуй пункти на кожен REQ (великий розрив має пояснюватися вимогами).
- Фільтр «за типом»: якщо є число, чи є граничні перевірки? Якщо є дія, чи є негатив? Якщо є умовна видимість, чи є стани?
